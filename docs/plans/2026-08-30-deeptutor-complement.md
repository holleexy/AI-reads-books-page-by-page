# DeepTutor と page-by-page 抽出の関係

日付: 2026-08-30

## 置き場所

- 上流: `/opt/deeptutor`（`https://github.com/HKUDS/DeepTutor.git`、契約上 v1.5.8）
- Hermes 側: `/opt/hermes-cli` はランタイム（compose / systemd / BWS）。ソース本体ではない
- 接続: `ssh -L 3782:127.0.0.1:3782 vps /opt/hermes-cli-prod/bin/deeptutor-stack connect`

## 役割の切り方

このリポジトリは **抽出器**。PDF を1ページずつ読み、学習可能な知識点の JSON と最終要約 Markdown を出す。検索も習熟度も持たない。

DeepTutor は **学習ランタイム**。資料を KB に載せ、引用付き対話、クイズ、Mastery Path（`knowledge_points` + モジュール）、記憶を持つ。

同じ「知識点」という言葉でも、こちらは自由文のリスト、DeepTutor は `id` / `name` / `type`（concept 等）/ `module_id` を持つ進捗オブジェクト。そのままは繋がらない。

## 補完すると何が実現するか

いま手元にあるのは、本を読んだ痕跡（JSON と要約ファイル）だけ。質問にも、抜けの診断にも、復習予定にもならない。DeepTutor に載せると、同じ材料が学習面になる。

いまある本（労務入門、採用入門、BtoBグロース、社内SE、バックオフィス）を例にすると、次が実現する。

1. **本に聞ける。** OCR PDF を KB に載せる。チャットで「採用は成果→事業→組織の順で考える理由は？」と聞くと、ページ引用つきで返る。要約ファイルを目で探す必要がなくなる。
2. **何を覚えたかが見える。** 抽出した知識点を Mastery Path のモジュールにする。診断→説明→ファインマン確認→演習→間隔復習が回る。採用入門なら「100のツボ」単位が自然。2686件を全部ポイントにすると多すぎるので、章・ツボへ束ねる。
3. **重要箇所だけのクイズ。** 抽出器は目次・索引を捨てている。そのリストから出題すると、OCR のゴミや柱ではなく、定義・枠組み・手順が問われる。
4. **横断して聞ける。** 労務・採用・バックオフィスを一つの KB にする。「採用が失敗したあとの労務リスクは？」のように、冊をまたいだ質問が引用つきで返る。
5. **前提を持った対話。** 最終要約を Notebook / Skill にすると、毎回「この本は何か」から始めなくてよい。Partner に同じライブラリを渡せば、同じ本を前提にした相談相手になる。

抽出だけだと「読んだ記録」。DeepTutor だけに PDF を投げると「全文検索に近い対話」。両方だと「重要な点を正本にした、聞ける・試せる・復習できる本」になる。

やらないこと: 同じ PDF を両方で抽出し直さない。2000件超の知識点を無加工で Mastery に流し込まない。

## やらないこと

- 同じ PDF を両方で「抽出の正本」にしない（二重課金、二重 SSOT）
- Hermes の CS glossary 突合と、Kindle 本パイプラインを一つのオントロジーに混ぜない
- DeepTutor の上流 checkout をこのリポジトリから直接いじらない
