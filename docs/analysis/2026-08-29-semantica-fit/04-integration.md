# つなぎ方の選択肢と落とし穴

Semantica の Git リポジトリをこのリポジトリの中へコピーする必要はない。
依存として `pip install semantica` し、下流スクリプトから呼べば足りる。
ソースを submodule にすると、51,000 行規模の別プロダクトを一緒に保守することになる。

## 入力の選び方

つなぐなら、入力は 3 つある。

**PDF を Semantica に直接渡す**は、一見短い。
しかしこのリポジトリがすでに捨てている目次や奥付を、再び Semantica 側で処理することになる。
日本語概念のパターン NER は弱い。
OCR PDF のノイズもそのままグラフに入る。
既存の約 10 万件は使われない。

**最終要約 Markdown を渡す**は、オントロジーの骨格を取るのに向く。
要約はすでに章立てされている。
`LLMOntologyGenerator.generate_ontology_from_text()` の入力長にも収まりやすい。
インスタンス（個別の事例、引用、数値）は落ちる。

**知識 JSON を渡す**が、本の情報をグラフにする本線である。
各知識点は、LLM がすでに「学習可能な命題」に圧縮している。
関係抽出の材料として、生ページよりノイズが少ない。
ページ番号は、これから読む分に付ける。
既存の文字列だけの件は、冊名付きのまま使う。
取り直さない。
詳細は [既存コーパスは取り直さない](12-no-full-reextract.md) に書いた。

## 推奨アーキテクチャ

既存パイプラインは触らず、完了後に一段足す。

```
Kindle / PDF inbox
  → OCR（必要なとき）
  → read_books.py（ページ LLM 抽出）
  → knowledge JSON + 最終要約          ← いまここまで
  → 新規: semantica 下流
       要約 → LLMOntologyGenerator（クラス）
       知識点 → LLM NER / Relation（インスタンス）
       → GraphBuilder（統合、デデュープ）
       → OWL / 可視化 / 問い合わせ
```

LLM はいまの xAI / Cursor 経路を流用できる。
Semantica の既定プロバイダは OpenAI と Groq である。
xAI をそのまま渡すには、薄いアダプタが要る。

## やってはいけないこと

**51 冊、約 10 万件を一度に LLM オントロジーへ投げない。**
トークンも費用も品質も壊れる。
まず 1 冊（例: 『労務入門』の最終要約でクラス、知識 JSON の先頭数百件でインスタンス）で形を見る。

**パターン NER だけで日本語の概念書をグラフ化しない。**
固有名は残るが、著者が立てた区分（守りの人事と攻めの人事など）がクラスにならない。

**Semantica に「本を読む」を置き換えない。**
再開、スキップ、Kindle、OCR inbox、冊管理はこちらが強い。
Semantica は構造化の段だけを担当させる。

**ページが無い既存件を、ページのために取り直さない。**
既存の JSON はページを持たない。
グラフのノードから元ページへは戻れない。
冊までは戻れる。
新規抽出のスキーマはすでに `{"text", "page"}` である。
既存件は取り直さない。

## より薄い代替

探索用のグラフだけなら、環境にある graphify でもフォルダからグラフは出る。
OWL、SHACL、PROV-O、エンティティ解決、矛盾検出までは持たない。
「本の概念体系をスキーマとして固定し、冊をまたいで問う」が目的なら Semantica の方が近い。
「まずつながりを眺めたい」だけなら graphify の方が導入が軽い。
