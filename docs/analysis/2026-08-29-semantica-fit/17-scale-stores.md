# 50冊以上・増加前提での置き場

判断日は 2026-08-30 である。
前提は次である。残る約 50 冊もグラフ化する。これから読む本も同じ下流に載せる。横断して問うことが最終形である。

結論は、**今 Neo4j も FAISS も入れなくてよい**である。
50 冊を止める欠落はグラフ DB ではない。
欠落は、冊ごとのグラフを再開付きで量産する経路と、LLM に渡す件数の予算である。

## いまの規模

2026-08-30 時点の知識 JSON は次である。

| 量 | 値 |
| --- | --- |
| 冊 | 51 |
| 知識点 | 106,414 |
| ページ付き | 0 |
| 最終要約がある冊 | 51 |
| Semantica グラフがある冊 | 1（『労務入門』、試し読み） |
| 1 冊の件数 | 最小 543、中央 2,065、最大 4,058 |

既定 `--limit 80` を 51 冊に適用すると 4,080 件である。
コーパスの 3.8% である。
50 冊を「やる」は、この既定のままでは足りない。

## Semantica 本体の既定

Hermes の Semantica 0.6.5 では、グラフ DB の既定は `memory` である。
選択肢に `neo4j`、`falkordb`、`neptune` がある。
ベクトルの既定は `faiss` である。
どちらも **製品の全パイプラインを常時動かすとき** の話である。
このリポジトリが呼んでいるのは抽出・グラフ構築・OWL 書き出しまでである。
その範囲はファイルに落ちる。

## 役割の切り分け

| 置き場 | 問いに答える単位 | 50冊超で要るか |
| --- | --- | --- |
| `book_analysis/semantica/{book_key}/` | 1 冊の項目と結び | 要る。これが本線 |
| FAISS（ローカル索引） | 名前が一致しない近い項目、冊をまたいだ候補 | 横断検索と用語寄せの段で要る |
| Neo4j | 統合グラフへの Cypher、増分 upsert、同時利用 | 統合グラフを常用面にしたあとで要る |

ファイル 51 ディレクトリは、ディスクとしてもメモリとしても小さい。
1 冊を開いて辿る処理に Neo4j は不要である。
51 冊の JSON を一度に RAM へ載せても、いまの件数なら DB 必須にはならない。

FAISS はサーバーではない。
Python ライブラリと索引ファイルである。
Semantica の vector backend 既定がそれである。
「近い概念」と「別の本の言い方」は、項目名の一致では解けない。
横断の前段として、ファイルの次に足す。

Neo4j は別プロセスのグラフ DB である。
運用（起動、バックアップ、認証）が乗る。
冊フォルダを増やすだけの増加には見合わない。
統合して「労務はどの本で何と結ばれているか」を常用してから入れる。

## 本当の制約

50 冊をグラフにする費用と時間は、FAISS / Neo4j ではなく LLM 呼び出しである。
知識点 106,414 件へ NER と関係抽出を全部かけると、トークンと待ちが冊グラフの書き出しを支配する。
ページ番号のための取り直しはしない。
入力は既存 JSON のままである。

増加する本は、要約ができたあと 1 ディレクトリを足す。
その増分はファイルと相性がよい。
統合グラフへ足す作業は、あとの段である。

## 入れる順

1. 要約済みの冊を、再開付きで Semantica 下流に通す。出力は冊ディレクトリのまま。品質ゲートは既存の出口を使う。
2. 冊グラフが並んだら、項目名・定義・必要なら知識点テキストの FAISS 索引を冊 namespace で作る。横断の「近い項目」と EntityResolver の候補に使う。
3. 横断統合を常用の問い合わせ面にしたら Neo4j を足す。そのときファイルはソース・オブ・レコードのまま残してよい。

1 を飛ばして 2 や 3 から始めない。
索引も DB も、冊グラフが無いと空である。

## 変えない制約

- Hermes の `semantica-knowledge-work.json` には書かない。
- このリポの `.venv` へ `pip install semantica` しない。
- 既存約 10 万件をページのために取り直さない。
- 51 冊を一度の LLM オントロジー呼び出しに投げない。
- 横断統合は冊グラフのあとである。
